# 案例：在樹莓派上跑一群常駐 agent

[English](case-study.md) | 繁體中文

`agent-perch` 是通用工具。這篇記錄它的出處環境，以及刻意沒有通用化的部分。

## 環境

約十個長時間運行的 Claude Code agent，各自在獨立的 tmux session，各自透過自己的 webhook 接 Telegram。一台樹莓派、一個 Unix 使用者、前面一台家用路由器。

## 入口：訊息必須送到正確的 agent

- 每個 agent 在不同的 localhost port 跑一個小 webhook server。nginx 依 URL 路徑前綴轉到對應 port，所以一個 TLS 網域、一個路由器轉發 port 就能服務所有 agent。
- 請求只有在帶有註冊 webhook 時訊息平台回傳的密鑰 token、且只有單一白名單使用者 id 時才會被採信，其餘一律丟棄。
- 白名單使用者送出 `/clear`、`/compact` 兩個固定指令時，會被打進該 agent 自己的 pane。固定文字、已驗證的寄件者、模型看不到任何內容。任何要在 agent 之間傳遞實際內容的東西都走檔案 mailbox（原因見 README）。

## 線上實際遇到的故障與對應修法

| 症狀 | 原因 | 修法 |
|---|---|---|
| agent 默默不再回應 | tmux session 死了 | 存活檢查＋重啟（現在的 `tick`） |
| session 還在、不回應、畫面停在互動選單 | 卡在沒人能按的按鍵提示 | 畫面不變「且」有已知 marker 的規則 |
| session 還在、畫面正常、訊息收不到 | agent 的 channel 子行程死了，harness 沒有重新拉起（已知上游問題） | 行程樹檢查（現在的 `health_cmd`） |
| 每次重啟後都出現同一個對話框 | 是 harness 的確認提示，不是模型狀態 | 用它自己的預設按鍵回應（現在的 `auto_replies`） |
| 訊息不再進來、但本機所有行程都正常 | 外部路徑壞了：nginx redirect、路由器 port forward、動態 DNS 記錄 | 外部探測，並透過獨立的 bot 告警，因為重啟 agent 修不了。與環境綁定，所以沒放進工具 |
| 不明原因重開機 | 電源或過熱 | 開機告警，附上樹莓派的欠壓與降頻旗標，因為當時 system journal 只存在記憶體，事後常無法還原原因 |

## 刻意沒有通用化的部分

- 外部路徑探測、開機診斷、整機備份：依賴這個網路與這個硬體。
- 額度用盡偵測：仍然只觀察。必須先從真實發生的情況抓到確切的橫幅文字，才有可能設計自動切換，所以偵測器只記錄與告警，不動任何東西。
- 在模型供應商之間容錯切換的路由 proxy：建好、測過、又移除了。它想用的免費額度實測不可用，第二個帳號的額度也與第一個並不獨立。

## 心得

1. 用兩個弱訊號一起判斷（畫面不變＋marker），不要信一個看起來很強的訊號。
2. 對「狀態轉變」告警，不要對「狀態」告警，否則告警會被靜音。
3. 修不了的事（為了壞掉的路由器重啟 agent）就改用另一條路徑通知人，不要無限重試。
4. agent 之間的內容不要打進對方的終端機。

## 限制（刻意為之）

單機、單租戶。沒有每個 agent 的 CPU／記憶體上限（下一步是 cgroups／ulimit）。沒有驗證、沒有密鑰管理、agent 之間沒有隔離（共用同一個 Unix 使用者）。要代管別人的 agent，這三樣都需要；那是路線圖，尚未實作。
